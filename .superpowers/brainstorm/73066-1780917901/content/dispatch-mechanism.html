Spring Boot → Python 任务下发机制

砍掉 FastAPI 后，Spring Boot 如何直接调度 Python 爬虫？

A

直连 Redis/Celery 队列

Spring Boot 用 Lettuce/Jedis 直接向 Redis Broker 推送 Celery 任务消息（JSON）。Python Celery Worker 保持不变，继续从 Redis 拉取执行。Spring Boot 也直接读 Redis Backend 获取结果。

Pros

  • Python 侧改动最小（Celery Worker 不动）
  • 砍掉 FastAPI，减少一跳
  • Redis 已有基础设施

Cons

  • Spring Boot 需理解 Celery 消息协议
  • Java ↔ Python 任务序列化兼容性
  • 结果回读需自维护
B

消息队列解耦 (RabbitMQ/Kafka)

Spring Boot 发布任务到 RabbitMQ Topic。Python 消费任务并发布结果到 Result Queue。Spring Boot 消费结果写库。完全异步、双方不直接感知对方存在。

Pros

  • 完全解耦，双方各自独立演进
  • 天然支持重试/死信/延迟队列
  • 可观测性强（消息堆积、消费速率）

Cons

  • 引入新中间件，运维成本增加
  • Python 侧需从 Celery 改为纯 pika/kafka 消费者
  • 异步回调链路长，调试复杂
C

轻量 Python 执行器 + gRPC/HTTP

FastAPI 缩为一个无状态的 Python 微服务（不经过 Celery），暴露 gRPC 或 REST 端点，Spring Boot 直接调用。Python 侧用 asyncio + aiohttp 并发执行爬取逻辑。

Pros

  • 同步/异步调用均可，调试直观
  • gRPC 序列化强类型，Java 原生支持
  • Python 用 async 解决阻塞问题

Cons

  • 仍保留一层 HTTP/gRPC 调用（虽然更薄）
  • 长任务（站点全量同步）需要流式或超时处理
  • 需要将 Celery 逻辑提取为独立可调用函数

架构对比一览

维度 A: 直连 Redis B: 消息队列 C: gRPC 执行器
Python 改造量 🟢 最小 🟠 中等 🟡 中等
解耦程度 🟡 紧 (Redis) 🟢 松 (消息) 🟡 中等
新中间件 🟢 无 🔴 需引入 🟢 无
实时性 Worker 拉取 即时推送 同步/流式
任务追踪 Redis Backend DB 持久化 DB 持久化
