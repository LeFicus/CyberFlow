Python 执行器架构选择

消息队列确定后，Python 侧用什么消费任务并执行爬虫？

A

保留 Celery，切换 Broker

Celery Worker 保持不变，Broker 从 Redis 换为 RabbitMQ（Celery 原生支持）。Spring Boot 通过 RabbitMQ 推送 Celery 协议消息。Python 侧几乎不改任务执行逻辑。

Pros

  • Celery 生态成熟：重试、限流、监控、定时任务
  • Service 层代码零改动
  • 运维团队熟悉 Celery

Cons

  • 仍依赖 Celery 框架（同步 httpx 仍阻塞 Worker）
  • Celery 消息协议对 Java 不够友好
  • concurrency=1 限制仍在
B

纯消息消费者 + asyncio

抛弃 Celery，用 pika (RabbitMQ) 或 aiokafka 写纯 Python 消费者。爬取逻辑改为 async/await + aiohttp/httpx-async，彻底解决同步阻塞问题。Spring Boot 推送标准 JSON 消息。

Pros

  • async 并发，单 Worker 可并行爬多个站点
  • 消息格式完全自控，Java 侧友好
  • 无框架束缚，性能更优

Cons

  • 需重写任务调度逻辑（重试、限流、超时等）
  • Scrapy 不原生支持 async，需子进程包装
  • 开发调试成本更高
C

混合：Celery (站点/订单) + 纯消费者 (Scrapy)

站点和订单爬取保留 Celery + RabbitMQ（稳定可靠，不需要高并发），Scrapy 商品爬取用纯消费者 + 子进程（隔离性好，资源独立）。两套执行器共存。

Pros

  • 渐进式迁移，风险低
  • 站点/订单逻辑几乎不动
  • Scrapy 进程隔离避免内存泄漏

Cons

  • 两套执行器增加复杂度
  • 监控运维需要覆盖两种模式

决策速览

维度 A: Celery+RabbitMQ B: 纯消费者+async C: 混合渐进
代码改造量 🟢 最小 🔴 大 🟡 中等
并发能力 🟠 同步阻塞 🟢 高并发 🟡 分场景
运维复杂度 🟢 低 🟠 中高 🟡 中
迁移风险 🟢 低 🔴 高 🟢 低
